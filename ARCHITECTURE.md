# Nutridrop Architecture

## Scope

The first backend milestone accepts explicit nutrition quantities from ChatGPT
and stores them durably. Delivery to the iPhone and Apple Health is a later
milestone.

The product is append-only. It does not infer nutrition values, edit existing
records, delete HealthKit samples, or provide a browser dashboard.

## Backend MCP

`nutridrop-mcp-staging` is one stateless Cloudflare Worker using Streamable
HTTP. It owns the D1 binding directly and exposes:

```text
POST /mcp
GET  /.well-known/oauth-protected-resource
```

There is no separate REST API Worker in this milestone.

The MCP server exposes one tool:

```text
record_nutrition
```

The tool accepts:

- One RFC 3339 consumption timestamp, including its offset.
- An optional user-facing meal label.
- One or more explicit nutrient, value, and unit quantities.

It accepts only allowlisted nutrition types and compatible units. It never
accepts a food description in place of quantities or estimates missing values.
The result confirms persistence for future iPhone sync; it does not claim that
Apple Health was updated.

## Authentication

WorkOS AuthKit is the shared identity provider for ChatGPT and iOS.

The MCP Worker publishes OAuth protected-resource metadata pointing to the
WorkOS authorization server. WorkOS uses OAuth Authorization Code with PKCE
and Client ID Metadata Documents for ChatGPT. The staging `/mcp` URL is the
default WorkOS resource indicator.

On every MCP request the Worker:

1. Reads the bearer access token.
2. Verifies its signature against the WorkOS JWKS.
3. Verifies issuer, MCP audience, expiry, and the `openid` scope.
4. Derives the database identity exclusively from the verified `sub` claim.

The client never provides a user ID as tool input.

## Data Model

The initial D1 database has one `nutrition_records` table:

- `id`: backend-generated UUID.
- `workos_user_id`: verified WorkOS `sub`.
- `ingestion_id`: backend-generated identifier reserved for future ingestion
  deduplication.
- `consumed_at`: validated RFC 3339 timestamp stored as text.
- `meal_label`: optional text.
- `nutrition_data`: validated quantities encoded as JSON.
- `schema_version`: JSON payload version, initially `1`.
- `created_at`: backend creation timestamp.

Record IDs are generated by the Worker; the model never supplies infrastructure
identifiers. Reliable retry deduplication is deferred until the client exposes
a stable invocation identifier. Quantities remain versioned JSON until delivery
or querying requirements justify normalized tables.

## Security

- Nutrition values and access tokens are never logged.
- MCP request bodies are bounded before parsing.
- Inputs use strict schemas, bounded arrays, finite positive values, and
  allowlisted nutrient/unit combinations.
- D1 statements are parameterized and all records are scoped to verified
  WorkOS identity.
- Worker configuration contains only public issuer and resource identifiers;
  secrets must use Cloudflare secrets.

## Deferred Work

- Public iOS API and access-token refresh.
- Device registration and active-writer selection.
- Normalized quantity and delivery tables.
- Foreground and background iPhone synchronization.
- HealthKit writing and acknowledgements.
- Cloudflare Queues, APNs, retries, and reconciliation.
- Retention, export, deletion, and public plugin submission requirements.

When delivery work begins, D1 remains the source of truth. The iPhone will pull
pending records, and push notifications will only be best-effort wake-up hints.
