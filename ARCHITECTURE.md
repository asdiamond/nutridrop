# Nutridrop Architecture

## Scope

The backend accepts explicit nutrition quantities from ChatGPT and stores them
durably. A silent push triggers iOS to fetch pending records from the same Worker
and save them locally. With explicit user permission, iOS writes them to Apple
Health and acknowledges successful records to the backend.

The product is append-only. It does not infer nutrition values, edit existing
records, delete HealthKit samples, or provide a browser dashboard.

## Backend MCP

`nutridrop-mcp-staging` is one stateless Cloudflare Worker using Streamable
HTTP. It owns the D1 binding directly and exposes:

```text
POST /mcp
GET  /.well-known/oauth-protected-resource
```

The same Worker also exposes authenticated iOS API routes:

```text
GET /v1/session
GET /v1/nutrition/pending
POST /v1/nutrition/acknowledge
```

There is no separate REST API Worker.

The MCP server exposes one tool:

```text
record_nutrition
```

The tool accepts:

- One RFC 3339 consumption timestamp, including its offset.
- An optional user-facing meal label.
- One or more explicit nutrient, value, and unit quantities.

It accepts only allowlisted nutrition types and compatible units. It never
accepts a food description in place of quantities or estimates missing values.
The result confirms persistence for future iPhone sync; it does not claim that
Apple Health was updated.

## Authentication

WorkOS Connect is the single authorization system for iOS and MCP clients.
Both use the same environment, issuer, signing keys, and resource audience.
iOS uses its own public Connect client with S256 PKCE; generic MCP clients use
their own OAuth registrations. Neither client sends an ID token to the API.

One `verifyAccessToken` function gates `/mcp` and `/v1/session`, returning only
`{ userId }` from the verified `sub`. The session endpoint returns that identity
to iOS. Nutrition storage uses it as `workos_user_id`, regardless of client.
There is no AuthKit-session-token verifier, token exchange bridge, or fallback.

The MCP Worker publishes OAuth protected-resource metadata pointing to the
WorkOS authorization server. WorkOS uses OAuth Authorization Code with PKCE
and Client ID Metadata Documents for ChatGPT. The staging `/mcp` URL is the
default WorkOS resource indicator.

On every authenticated API or MCP request the Worker:

1. Reads the bearer access token.
2. Verifies its signature against the WorkOS JWKS.
3. Requires RS256, the configured issuer/resource audience, expiry, issued-at,
   a user subject, and the `openid` scope.
4. Derives the database identity exclusively from the verified `sub` claim.

The client never provides a user ID as tool input.

## Data Model

The initial D1 database has one `nutrition_records` table:

- `id`: backend-generated UUID.
- `workos_user_id`: verified WorkOS `sub`.
- `ingestion_id`: backend-generated identifier reserved for future ingestion
  deduplication.
- `consumed_at`: validated RFC 3339 timestamp stored as text.
- `meal_label`: optional text.
- `nutrition_data`: validated quantities encoded as JSON.
- `schema_version`: JSON payload version, initially `1`.
- `created_at`: backend creation timestamp.
- `healthkit_acknowledged_at`: first server acknowledgement timestamp, or null
  while still pending. Acknowledged records are retained, not deleted.

Record IDs are generated by the Worker; the model never supplies infrastructure
identifiers. Reliable retry deduplication is deferred until the client exposes
a stable invocation identifier. Quantities remain versioned JSON until delivery
or querying requirements justify normalized tables.

## Security

- Nutrition values and access tokens are never logged.
- MCP request bodies are bounded before parsing.
- Inputs use strict schemas, bounded arrays, finite positive values, and
  allowlisted nutrient/unit combinations.
- D1 statements are parameterized and all records are scoped to verified
  WorkOS identity.
- Worker configuration contains only public issuer and resource identifiers;
  secrets must use Cloudflare secrets.

## Delivery And HealthKit

APNs submission runs in the existing Worker's Queue consumer, published after
each saved record. Transient failures retry five times at 60-second intervals.
There is intentionally no outbox or dead-letter queue.

One push destination per user is stored in `push_tokens`. Registration reassigns
token ownership when an installation changes accounts. DELETE is conditional
on both the user and destination. This is not a HealthKit writer lease.

iOS fetches pending nutrition in 50-record pages after a push, atomically saving
records and paging progress per account. After explicit opt-in, it checks write
authorization and saves each record as an atomic array of dietary samples.
Stable HealthKit sync identifiers encode user, record and nutrient; sync version
1 makes crash retries repeat the same logical samples. No HealthKit reads are used.

Local state transitions from downloaded to written to synced. Written is saved
before acknowledgement so network retries do not repeat HealthKit writes.
Permission/write failures remain pending. Push, manual sync, and foreground entry
retry unfinished work. Apple can cache writes while locked until unlock.

## Deferred Work

- Notification reconciliation and outbox, if justified by observed failures.
- Retention, export, deletion, and public plugin submission requirements.
- Multi-device writer coordination beyond the current single push destination.

D1 remains the source of truth for pending nutrition; pushes are best-effort
wake-up hints. The backend trusts user-scoped acknowledgements of HealthKit writes.
